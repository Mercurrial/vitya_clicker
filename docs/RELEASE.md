# Как выпустить версию

## Коротко: что делаете вы

Всю подготовку делает чат. Руками — пять шагов.

1. **Попросить чат:** «подготовь выпуск версии 1.0.0 по docs/RELEASE.md».
   Он всё проверит, поднимет версии (у первого выпуска они уже стоят),
   снимет эталонный сейв, запишет CHANGELOG и откроет PR.
2. **Посмотреть PR.** Проверка «Проверка PR» зелёная — вместе со снимками
   экрана. В CHANGELOG написано то, что вы готовы показать друзьям. Снимки,
   которые переснимали, вы видели во вкладке Files changed.
3. **Влить PR.** Сайт от этого ещё не меняется.
4. **Поставить тег** — это и есть кнопка «выпустить». Номер тот же, что в
   `pubspec.yaml`:
   ```bash
   git switch main
   git pull
   git tag v1.0.0
   git push origin v1.0.0
   ```
   Или сказать чату «поставь тег v1.0.0 на main»: без вашего слова он
   тег не ставит.
5. **Через 2–3 минуты** открыть https://mercurrial.github.io/vitya_clicker/
   и обновить страницу. Выкладка во вкладке Actions красная — нажать
   **Run workflow** и выбрать тег. Не Re-run.

---

Дальше — подробный порядок, по которому работает чат. Проверен на
тестовых сборках 1.0.0 и 1.1.0.
Шагов немного, но пропускать нельзя ни один: каждый закрывает конкретный
способ испортить чужой прогресс.

---

## 1. Проверить, что ничего не сломано

```bash
flutter analyze                                   # должно быть пусто
flutter test                                      # все зелёные
flutter test --tags perf --run-skipped            # замеры, на спокойной машине
```

**Снимки экрана** (`test/goldens/`) сверяет «Проверка PR», работа «Снимки
экрана». Эталон снят на одной платформе — ubuntu-latest с Flutter 3.24.3 в
GitHub Actions — и сверяется там же. На Windows шрифты рисуются иначе, и
локально снимки с текстом не совпадут. Это ожидаемо: локально их не
переснимать и не коммитить.

Посмотреть на снимки глазами всё равно надо. Дважды вёрстка ломалась так,
что ни анализатор, ни тесты этого не видели.

**Если снимок не совпал** — это ещё не поломка. Тест говорит только «экран
стал другим», а не «экран стал хуже». Порядок такой:

1. Открыть упавшую проверку (в PR: Details → Summary) и скачать внизу
   архив `goldens-failures`. На каждый снимок в нём `_maskedDiff.png` —
   подсвечено, что разъехалось, — а ещё эталон `_masterImage.png` и новый
   кадр `_testImage.png`.
2. Решить глазами: это то изменение, которое вы делали намеренно?
3. Да — переснять: Actions → **Переснять снимки** → Run workflow → ветка
   PR. Или из терминала: `gh workflow run goldens.yml --ref <ветка>`. Через
   3–4 минуты в ветке появится коммит «Переснять снимки экрана», и
   workflow сам запустит проверку заново. Затем **посмотреть на новые
   снимки** в PR, вкладка Files changed: GitHub показывает старую и новую
   картинку рядом (2-up), шторкой (Swipe) или наложением (Onion skin).
4. Нет — чинить вёрстку.

Обновлять эталон не глядя нельзя: тогда он перестаёт что-либо стеречь.

Чат, который работает в этой ветке локально, после пересъёмки делает
`git pull`: иначе его следующий push откажет.

## 2. Проверить баланс

```bash
dart run tools/balance_report.dart 4
```

Цели описаны в `lib/sim/balance_targets.dart`, их же стережёт
`test/balance_test.dart`. Отчёт нужен, чтобы посмотреть на кривую целиком,
а не только на «попали/не попали».

## 3. Если менялся баланс

**У первого выпуска этот шаг пропускается.** Пока в `test/fixtures/` нет ни
одного эталона, версия баланса — 1, в журнале одна запись, и
`release_contract_test.dart` не даст это нарушить. Правила ниже действуют
со второго выпуска.

Тест `release_contract_test.dart` не даст забыть, но порядок такой:

1. Поднять `kBalanceVersion` в `lib/content/balance.dart`.
2. Добавить запись в `kBalanceLog`: **что** изменилось и **почему**,
   человеческим языком.
3. Если игроку стало хуже — поставить `isNerf: true` и назначить
   `compensationWisdom`. Молча ронять чужой доход нельзя.
4. Обновить отпечаток в `release_contract_test.dart`.

Игрок увидит этот список при первом запуске новой версии, а компенсация
начислится до показа экрана.

## 4. Поднять версию приложения

В `pubspec.yaml`:

```yaml
version: 1.0.0+3      # +N обязателен: без него Android не поставит обновление
```

Номер сборки только растёт, даже когда имя версии пошло назад: выпуск
1.0.0 — `+3`, потому что у друзей стоит тестовая 1.1.0+2. Меньший номер
Android поверх не поставит. Это стережёт `release_contract_test.dart`.

## 5. Снять эталонный сейв

```bash
dart run tools/make_fixture.dart 1.0.0
```

Файл ляжет в `test/fixtures/` и **больше никогда не правится**. Это снимок
того, что реально лежит у игроков: каждая следующая версия обязана его
открыть. Проверяется автоматически.

**Первый эталон включает строгие правила.** С ним `release_contract_test`
начинает сверять отпечаток чисел баланса, а правило «до выпуска» больше не
действует. Поэтому в том же PR записать в тест действующий отпечаток — тест
сам подскажет, какой, упав на первом прогоне.

## 6. Записать изменения

`CHANGELOG.md` — для истории. Правки баланса игрок и так увидит в игре,
здесь они остаются на будущее.

## 7. Собрать

```bash
flutter build web --release      # для iPhone и всех остальных
flutter build apk --release      # для Android файлом
```

APK окажется в `build/app/outputs/flutter-apk/app-release.apk`.

## 8. Выложить

Шаги 1–7 делаются в ветке и приходят в `main` обычным PR. PR проверяется
автоматически — анализ, тесты и снимки экрана (`.github/workflows/ci.yml`), —
но замеры CI не гоняет, поэтому они из шага 1 всё равно за вами.

**Влитие в `main` сайт не трогает.** Сайт обновляет только тег версии —
его ставят на `main`, когда PR выпуска уже влит:

```bash
git switch main
git pull
git tag v1.0.0
git push origin v1.0.0
```

Тег запускает `.github/workflows/deploy-web.yml`: ещё раз анализ и тесты,
сборка, выкладка. Ссылка всегда одна и та же:

**https://mercurrial.github.io/vitya_clicker/**

Сборка занимает около двух минут, выкладывание — ещё десять секунд.
Раньше этого по ссылке будет старая версия, и это нормально. Ход сборки
виден на вкладке Actions репозитория.

Тег — только на `main` и только после влития. Тег на ветке выложит то,
чего в `main` нет, и следующий выпуск это молча откатит.

Выкладка упала — не жать Re-run: он загружает артефакт второй раз, и
выкладка падает снова. Нужно Actions → Deploy web to GitHub Pages →
**Run workflow**, в списке выбрать **тег**, а не `main`.

APK отправляется файлом. Подписан отладочным ключом — **ключ менять
нельзя**, иначе обновление не встанет поверх и придётся удалять игру
вместе с гаражом.

## Что нельзя делать никогда

**Менять уже написанную миграцию** в `lib/core/save.dart`. Миграция читает
то, что реально лежит у игрока на диске, а не то, чему равна константа
сегодня. Дублирование кода там намеренное.

**Править файлы в `test/fixtures/`.** Если эталон перестал читаться —
чинить надо код, а не эталон. Это единственное доказательство, что
обновление не потеряет прогресс.

**Класть в сейв производное число.** Доход, цена, мудрость — всё это
считается из фактов при загрузке. Стоит положить туда оценку, и правка
баланса перестанет действовать на тех, кто уже играет. Список запрещённых
ключей стережёт `balance_update_test.dart`.

**Менять ключ подписи APK.** См. выше.

---

## Если что-то пошло не так после выпуска

Сейв игрока никуда не делся: он хранит факты, а не оценки. Почти любую
ошибку баланса можно исправить следующей версией — числа применятся к
старым сохранениям сами, без миграции.

Настоящая беда одна: сломанный формат сейва. От неё защищают эталоны из
`test/fixtures/` и цепочка миграций. Поэтому шаг 5 — не формальность.
